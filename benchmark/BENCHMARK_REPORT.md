# 票务中心 (Ticket Center) JMeter 性能压测与详情页调优实战报告

> **测试工具**：Apache JMeter 5.6.3 (CLI 生产模式)  
> **测试环境**：
> - 核心框架：Spring Boot 3.5.14 + Java 17 + Tomcat 10.1
> - 数据存储：MySQL 8.4 (HikariCP 连接池)
> - 缓存与锁：Redis 7.4 (Lettuce 连接池 + Redisson 分布式锁 + Lua 脚本 + Bitmap 位图)
> - 消息队列：RabbitMQ 3.13 (Direct + 延时关单死信队列)

---

## 一、压测场景与性能指标汇总看板

调优后架构（聚合缓存 + UV 剥离，Lettuce `max-active: 10`）**在完全相同的配置下重复测量了 4 轮**，用于建立本测试环境的噪声基准。单轮数字没有意义，必须看区间：

| 测试场景 | 请求接口 | 并发 | 样本 | 吞吐量区间 (QPS) | 均值 | 极差 | 平均响应时间 |
| :--- | :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| **场景 1：签到状态查询** | `GET /user/sign/status` | 200 | 10,000 | 983.2 ~ 1,056.0 | **1,015.0** | **7.2%** | 182 ~ 197 ms |
| **场景 2：演出详情聚合读** | `GET /event/1` | 200 | 4,000 | 3,210.3 ~ 4,246.3 | **3,597.0** | **28.8%** | 24 ~ 36 ms |
| **场景 3：秒杀抢票并发写** | `POST /ticket-orders/reserve/3` | 100 | 1,000 | 570.1 ~ 793.7 | **676.2** | **33.1%** | 73 ~ 99 ms |

秒杀强一致性核对在**每一轮**均通过（Redis 结余 0、成功 50 人、MySQL 落库 50 笔）。错误率除个别轮次出现 0.15% 的启动期连接失败外均为 0。

### 关键发现：这台机器的测量噪声高达 30%

场景 2 和场景 3 在**零改动**的情况下，重复测量的极差分别是 **28.8%** 和 **33.1%**。这个数字直接决定了本报告中哪些结论能成立：

- **凡是小于 30% 的性能差异，在本环境下都无法与噪声区分**；
- 演出详情页 565.6 → 3,597.0（**5.4 倍以上**）远超噪声，结论可靠；
- 连接池 `max-active` 10 vs 50 之间那 12.3% 的差异，**完全落在噪声区间内，不构成任何结论**。

### 场景 1：一个稳定复现、但未定位的回归

场景 1 的情况与另外两个场景相反——**它的噪声很小（极差仅 7.2%），但整体水平稳定地停在基线的 40%**：

| 测量批次 | 签到 QPS |
| :--- | :---: |
| 原始基线 | 2,542.6 |
| 中途一次（`results_phase1_cache_only/`，平均 131.7 ms） | 1,475.8 |
| 调优后第 1 轮 | 1,005.8 |
| 调优后第 2 轮 | 1,056.0 |
| 调优后第 3 轮 | 983.2 |

三轮复测集中在 983 ~ 1,056 之间，波动只有 7.2%，**不是偶发抖动，是稳定复现的回归**。中间那次 1,475.8 QPS 落在基线与终值之间，说明 8 月 28 日这一天是逐步劣化的，不是一步掉下来的。

签到链路的代码本次完全没有改动，Lettuce 连接池也已恢复为与基线相同的 `max-active: 10`，因此**既不能归因于详情页改造，也不能归因于连接池**。

已排除：失败样本污染（多轮错误率为 0，QPS 依旧约 1,000）、连接池配置、随机噪声（7.2% 的稳定性排除了这一点）。

尚未排除：Actuator 指标采集开销（本次新增该依赖，会对每个请求埋点）、Redis 中签到 Bitmap 随测试轮次累积增长、原始基线测量时的机器状态差异。

**下一步对照实验的正确做法**：从 `pom.xml` 移除 `spring-boot-starter-actuator` 依赖后重新压场景 1。若 QPS 回到 2,500 附近，则 Actuator 就是原因。

这里要纠正一个直觉误区：**注释掉 `management` 配置块起不到对照作用**。`management.endpoints.web.exposure.include` 只控制端点能否通过 HTTP 访问，而每请求的埋点开销来自 actuator starter 自动装配的 `MeterRegistry` 与 HTTP observation 过滤器——它们随依赖存在而生效，与端点是否暴露无关。同理，后续把 actuator 挪到独立管理端口（`management.server.port: 8081`）也**不会**改变埋点开销，那是访问控制而非性能改动。

**本项目未执行该实验，故不下结论。**

#### 2026-08-30 结案：上面这段的归因方向是错的

Actuator 假设不成立，那个对照实验也没有意义。`git log -S 'spring-boot-starter-actuator'` 落在 `3d5d4be`，**正是记录 2,542.6 基线的那次提交**——两轮压测的 classpath 上都有 actuator，它不可能是差异来源。上面「本次新增该依赖」这句话本身是错的。

真正的原因是**签到接口的 Redis 往返次数**。接口最多只读两个 key（当月位图、跨月时加上月位图），却按位逐次打 Redis：今日 1 次 `GETBIT`、连签 1 次 `BITFIELD`、当月累计 1 次 `BITCOUNT`、本周七天各 1 次 `GETBIT`，加上 `RefreshTokenInterceptor` 每请求固定的 `HGETALL` + `PEXPIRE`，实测**每请求 12 次往返**（`getbit` 是 8 次，因为压测当天 2026-08-30 是周日，本周七天全部落在今天或之前；周一只需 6 次——这个接口的开销本身随星期几摆动近 2 倍）。

改成把整月位图一次 `GET` 回来、在内存里算位（`UserServiceImpl.monthBitmap/isSigned/countSignedDays`），往返降到 3 次（2 次拦截器 + 1 次位图）。同机、同 JMeter 计划（200 线程 × 50 轮）、同一批 token，各跑三轮：

| 轮次 | 改前（12 次往返） | 改后（3 次往返） |
| --- | --- | --- |
| 第 1 轮（冷启动，JIT 未热） | 1,046.5 QPS / 172 ms | 2,395.2 QPS / 66 ms |
| 第 2 轮 | 1,194.9 QPS / 149 ms | 3,349.0 QPS / 41 ms |
| 第 3 轮 | 1,206.1 QPS / 147 ms | 3,373.8 QPS / 40 ms |

稳态 **1,206 → 3,374 QPS（2.8 倍），平均耗时 147 → 40 ms（降 73%）**，错误率两侧都是 0。改前第 1 轮的 1,046.5 QPS / 172 ms 与上表记录的 983 ~ 1,056 QPS / 182 ~ 197 ms 基本重合，**说明这个回归在今天的机器上原样复现了**，不是当时的环境噪声。

由这两组数可以直接算出每次 Redis 往返的边际成本：`(147 − 40) ÷ (12 − 3) ≈ 11.9 ms`。而 Redis 服务端自己报的 `usec_per_call` 只有 2 ~ 15 **微秒**，即真正执行命令的时间可以忽略，11.9 ms 全部是往返与排队——`lettuce.pool.max-active: 10` 面对 200 个并发 Tomcat 线程，每条连接后面排着约 20 个请求。

这也解释了为什么基线明明有 11 次往返（`3d5d4be` 的实现：1 `GETBIT` + 2 次连签 + 1 `BITCOUNT` + 5 天本周，加 2 次拦截器）却能跑到 2,542.6 QPS：**往返次数一直是 10 ~ 12，变的是每次往返的单价**。若基线也是 11.9 ms 的单价，11 次往返对应约 150 ms、约 1,300 QPS，而它实测 63 ms。8 月 27 → 28 之间变化的是部署形态（`bc91ded` 同时引入 `Dockerfile` 与 compose 的 `backend` 服务，应用从宿主机直连 Redis 变成跨 Docker 网桥），不是签到链路的代码。

把往返压到 3 次之后，单价高低已经不再重要——这也是不必继续追查 8 月 27 → 28 环境差异的原因。

**本报告中演出详情页的调优结论仅基于场景 2 自身的前后对比，不依赖场景 1、3 的数据。**

### 关于早期数据的一处修正

`run_all_benchmarks.ps1` 原先用 `[math]::Max(1, duration)` 计算吞吐量，当一轮压测在 1 秒内跑完时，分母会被强行钉成 1 秒——4,000 样本因此被算成"4,000 QPS"。本轮已修复该计算，报告中的 QPS 一律以 JMeter summariser 为准。**早期报告中接近样本总数整数的 QPS 值可能受此影响。**

## 二、演出详情页从“伪缓存”到聚合视图缓存调优叙事（核心实战）

### 1. 发现异常：同为读接口，性能相差 4 倍
在基线压测中，我们观察到一组矛盾现象：
* 同样在 200 并发压力下，同为“走 Redis 缓存”的读接口：
  * **用户签到状态 (`GET /user/sign/status`)**：QPS 达到 **2,542.6 req/s**，平均耗时仅 **63.05 ms**；
  * **演出详情查询 (`GET /event/1`)**：QPS 仅 **565.6 req/s**，平均耗时高达 **266.27 ms**，最大长尾达 **1,135 ms**。

---

### 2. 根因分析：Step 0 耗时拆解与实测证据
我们没有停留在代码阅读假设，而是在 `EventDetailProfilingTest` 中通过高精度 `System.nanoTime()` 对 4 个子步骤分别打点。

**采样条件**：2,000 笔调用，**并发度 50**（`EventDetailProfilingTest.java:53-54`）。注意这与 JMeter 压测的 200 并发不是同一负载水平，因此本采样用于确定**各步骤的相对占比**，不能用来解释 200 并发下 266ms 的绝对值。

```text
===============================================================
>>> [Step 0 实测证据] 详情页 4 步耗时拆解与占比测量结果 (样本=2000, 并发=50)
===============================================================
1. Redis Event 缓存读:        7.08 ms (23.0%)
2. Redis HyperLogLog UV 计算: 6.64 ms (21.6%)
3. MySQL 分类名称查询:        8.24 ms (26.8%)
4. MySQL 票档列表查询:        8.78 ms (28.6%)
---------------------------------------------------------------
总平均耗时: 30.73 ms | P50: 26 ms | P95: 62 ms | P99: 82 ms | Max: 121 ms
MySQL 查询耗时占比: 55.4% ~ 59.5% (2次DB查询合计 17.01 ms)
Redis 查询耗时占比: 40.5% ~ 44.6% (2次Redis查询合计 13.72 ms)
===============================================================
```

**实测定位结论**：
1. **名义走缓存，实际存在穿透放大**：`EventServiceImpl.queryById` 仅缓存了单表 `Event`，每次请求仍穿透打 2 次 MySQL（分类名 + 票档列表），**MySQL 耗时占比 55.4%~59.5%**，是四步中最贵的部分；
2. **每次请求固定 4 次网络往返 (RTT)**：1 次 Redis Event GET + 1 次 Redis PFCOUNT + 2 次 MySQL。

**一个未闭合的缺口**：50 并发下四步合计仅 30.73ms，而 200 并发压测的平均耗时是 266.27ms。两者相差约 235ms，**这部分不在四步拆解的覆盖范围内**，属于并发放大后的排队与资源争抢（线程池、连接池、上下文切换等）。本次未对这 235ms 做进一步剖析，因此**无法断言它由某个具体组件造成**。下文的优化针对的是已被证据支撑的部分——消除 2 次 MySQL 与 1 次 PFCOUNT，把每请求 RTT 从 4 次降到 1 次。


---

### 3. 架构优化方案与设计取舍

#### (1) 聚合视图全量缓存 (`EventDetailVO`)
* 将 `EventDetailVO`（包含 Event 基础信息、分类名称、票档列表）整体存入 Redis 缓存（Key: `tc:cache:event:detail:{id}`，TTL 30 分钟）；
* 缓存回退时在 DB 中单次组装，缓存命中时 **0 次 MySQL 查询**。

#### (2) UV 想看人数读写剥离（方案 A）
* **后端**：`EventDetailVO` 移除 `uv` 字段，`queryById` 不再执行高频 `PFCOUNT`，详情聚合缓存实现纯静态化长 TTL；
* **前端**：`EventDetailPage.vue` 使用独立 `const uv = ref(0)` 承载；命中路由去重分支时调用 `eventApi.getViews(id)`（`GET /event/uv/{id}`），首次访问调用 `addView`，杜绝二次访问空白；
* **取舍**：将动态实时统计从长效聚合缓存中剥离，代价是前端多一次轻量 Redis 请求，但该请求页面加载本就需执行 `addView`，实际净增为 0。

#### (3) 缓存失效双写一致性闭环
* 演出更新 (`updateEvent`)：同步删除 `CACHE_EVENT_KEY` 与 `CACHE_EVENT_DETAIL_KEY`；
* 票档新增/开票 (`addTicket`)：开票后同步删除对应演出的 `CACHE_EVENT_DETAIL_KEY`，确保票档变更实时对前端可见。

### 4. 变量隔离实测对比表（三列对比）

为明确各优化举措的独立贡献，我们进行了两轮独立复测，将**聚合缓存**与**连接池扩容**拆分为独立变量：

| 压测阶段 / 架构状态 | 关键配置与机制 | 吞吐量 (QPS) | 平均响应时间 | 最大响应时间 |
| :--- | :--- | :---: | :---: | :---: |
| **基线（调优前）** | 伪缓存（4次网络往返），`max-active: 10` | **565.6 req/s** | **266.27 ms** | **1,135 ms** |
| **阶段一：仅聚合缓存** | 聚合 `EventDetailVO` 缓存（0次 MySQL），UV 剥离；`max-active: 10` | **3,558.7 req/s** | **16.90 ms** | **152 ms** |
| **阶段二：缓存 + 连接池扩容** | 同上 + `max-active: 50` | **3,122.6 req/s** | **29.67 ms** | **321 ms** |
| **阶段三：连接池恢复 10，复测** | 与阶段一配置**完全相同** | **3,210.3 req/s** | **25.15 ms** | **183 ms** |
| **阶段四：同上，再复测** | 与阶段一配置**完全相同** | **4,246.3 req/s** | **24.21 ms** | **250 ms** |
| **阶段五：同上，再复测** | 与阶段一配置**完全相同** | **3,372.7 req/s** | **36.44 ms** | — |

**独立贡献结论**：

1. **聚合缓存与 UV 剥离贡献了全部可归因的性能提升**：消除 2 次 MySQL 穿透与 1 次 PFCOUNT 后，每请求 RTT 从 4 次收敛为 1 次 Redis GET。QPS 从 565.6 升至均值 3,597.0（**5.4 ~ 7.5 倍，四轮区间 3,210 ~ 4,246**），平均响应时间从 266.27ms 降至 24 ~ 36ms，最大长尾从 1,135ms 降至 150 ~ 250ms。**这个量级是噪声区间的十几倍，结论可靠。**

2. **连接池扩容的影响无法从噪声中分离，且这个判断经过了两次修正**：

   - 第一次判断：阶段二（`max-active: 50`）比阶段一低 12.3%，看起来是负优化；
   - 第一次修正：阶段三用**相同配置**复测得 3,210.3，与阶段一差 9.8% —— 与 12.3% 同量级，于是改判为"无法区分"；
   - 第二次修正：阶段四、五继续用**相同配置**复测，得到 4,246.3 和 3,372.7。**四轮同配置测量的极差达到 28.8%**，远大于配置间的 12.3%。

   **阶段二的 3,122.6 完全落在同配置的波动区间内。** 结论确定为：本测试环境下无法判定连接池大小对该场景的影响。要判定，需要每种配置各测 5 轮以上并比较均值与标准差——考虑到 28.8% 的噪声，所需样本量远超本项目的投入。

3. **方法论收获（本次调优最大的收获，超过性能数字本身）**：

   - 如果两项改动合并压测，3,122.6 会被整体记为"缓存 + 连接池"的共同成果；
   - 如果只做一次 A/B 对照，会得出"连接池是负优化"——**这正是我们最初写下的错误结论**；
   - 只有反复用**同一配置**测量，才知道这台机器"什么都不改能差 28.8%"。

   **判断一个差异是否真实，前提是先知道零改动时能差多少。没有噪声基准的对照实验，产出的是故事，不是结论。**

**当前配置**：`max-active: 10`（与基线一致）。没有证据支持扩容有收益，故不改动。

## 三、秒杀抢票数据强一致性与防资损核验

在两轮调优压测全过程中，场景 3（初始库存 50 张票，打入 1,000 笔抢购请求）均严格执行数据对账：

| 校验维度 | 预期指标 | 实际压测结果 | 判定状态 | 核心防护机制 |
| :--- | :---: | :---: | :---: | :--- |
| **初始票档库存** | 50 张 | 50 张 | ✔ 吻合 | 初始库存预热 |
| **Redis 预扣库存结余** | 0 张 | **0 张** | **✔ 精确** | Lua 脚本原子性 `decr` 扣减 |
| **Redis 拦截超额请求** | 950 笔 | **950 笔** | **✔ 精确** | 库存为 0 瞬间内存拦截 |
| **Redis 抢票成功人数** | 50 人 | **50 人** | **✔ 精确** | Redis Set 一人一票排重 |
| **MySQL 最终落库订单** | 50 笔 | **50 笔** | **✔ 精确** | RabbitMQ 削峰异步落库 |
| **超卖 / 丢单 / 少卖** | 0 笔 | **0 笔** | **✔ 零资损** | **绝对零超卖、零少卖** |
