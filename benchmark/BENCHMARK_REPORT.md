# Ticket Center 性能压测报告

> **测量时间**：2026-09-03
> **工具**：Apache JMeter 5.6.3（CLI 模式，`-n -t -l -e -o`）
> **被测服务**：拆分前的单体版本（commit `c6f62acf`，单文件 `docker compose --profile full`），后端与中间件均在容器内
> **环境**：Spring Boot 3.5.14 / Java 17 / Tomcat 10.1、MySQL 8.4（HikariCP）、Redis 7（Lettuce `max-active: 50` + Redisson + Lua + Bitmap）、RabbitMQ 3.13

## 一、测量口径

三个场景连续跑 3 轮，每轮 15,000 个样本。数据取自 JMeter 官方 dashboard 的 `statistics.json`，**不取 summariser 那一行**。

两者对不上，而且差得不小——第 1 轮签到场景 summariser 报 1,793.1 req/s，dashboard 报 2,210.9，相差 23%。原因是 summariser 的分母是整个测试的墙上时钟并取整到秒（10000 ÷ 1793.1 = 5.577 s），而 10,000 个样本的实际跨度只有 4.523 s，中间那一秒多是 200 个线程的创建开销。从 JTL 原始文件重算得 2,216.3，与 dashboard 相差 0.24%，所以 dashboard 是可信的那个。

**客户端与服务端同机**，JMeter 自己也要吃 CPU，因此以下数字是"这台机器上该配置的相对表现"，不是服务端容量上限。

测量时 Redis 副本未参与复制，读写全部落在单个节点上，**以上数字反映的是单节点 Redis 的表现**。若副本正常复制，主节点需额外承担复制流量，吞吐可能略低于此。

## 三、两个容易读错的地方

### 第 1 轮不能当基准

容器刚重启，JVM 未预热。三个场景的第 1 轮分别只有稳态的 75%、63%、82%，详情页的差距最大——第 1 轮 2,530 对第 3 轮 4,499，相差 78%。这不是配置差异，是 JIT 编译和连接池预热的代价。

**报告里凡是给性能结论的地方都必须排除第 1 轮**，否则同一份代码能测出两个相差近一倍的"性能"。

### 秒杀的「错误率 0%」不代表 1,000 笔都抢到了

场景 3 的 1,000 个样本全是 HTTP 200、`success=true`，但真正下单成功的只有 50 个。剩下 950 笔是业务层拒绝——库存不足或已限购——响应体里 `code` 不是 200，但 HTTP 状态码是 200，JMeter 只看后者。

所以 1,012 ~ 1,101 req/s 衡量的是**这条链路在 100 并发下的处理能力**（含 Lua 预扣、排重判定与拒绝路径），不是每秒成功下单 1,000 笔。真实成交速率受库存约束，与吞吐量无关。

## 四、噪声：不确定性比数字本身更重要

稳态只有两轮，样本量薄，只能给出观测区间，不足以建立可靠的噪声基准。但已经能看出量级：

- 签到场景两轮相差 **5.0%**，比较稳；
- 秒杀场景相差 **8.8%**；
- 详情页两轮相差 **29.9%**——3,463 和 4,499，配置完全相同。

详情页这个 30% 直接决定了什么结论能成立：**在这台机器上，小于 30% 的性能差异无法与噪声区分**。要判定一个 10% 级别的优化是否真实有效，需要每种配置各测 5 轮以上比较均值与标准差，本次没有做到那个程度，所以不对小幅差异下任何结论。

历史上同机测过四轮同配置，详情页极差 28.8%，与本次的 29.9% 吻合。

## 五、秒杀强一致性核对

每轮压测结束后自动对账（初始 50 张票，打入 1,000 笔请求），**三轮全部通过**：

| 校验维度 | 预期 | 实际 | 防护机制 |
| :--- | :---: | :---: | :--- |
| Redis 预扣库存结余 | 0 | **0** | Lua 脚本原子扣减 |
| Redis 抢票成功人数 | 50 | **50** | Set 一人一票排重 |
| MySQL 落库订单数 | 50 | **50** | RabbitMQ 异步削峰落库 |
| 超卖 / 少卖 | 0 | **0** | 零资损 |

压测本身是抽样验证，正确性由自动化测试守住：`TicketReserveConcurrencyTest` 断言 200 线程抢 10 张时成功数恰好 10、库存精确归零、库存键缺失时不放行；`TicketOrderConsistencyTest` 覆盖死信补偿、重复投递幂等与超时关单。这两个测试跑在 Testcontainers 拉起的真实中间件上，不依赖手工压测复现。

## 六、当前运行方式

上面的数字来自旧单体版本，不能用新版脚本直接复现。当前入口已改为 Linux Bash，并按交易库和异步预约结果对账；详细环境要求见根目录 README。

```bash
# 先检查小规模链路
bash benchmark/run_all_benchmarks.sh smoke

# 再执行默认规模压测
bash benchmark/run_all_benchmarks.sh
```

需要 Java 17、JMeter 5.6.3、Python 3 和 Docker CLI。JMeter 不在 PATH 中时，在 Linux 终端通过 `export JMETER_EXEC=/path/to/apache-jmeter-5.6.3/bin/jmeter` 指定启动器。脚本为每轮新建专用票档、生成 Token，并将结果分别保存到 `results/<本轮编号>/` 和 `reports/<本轮编号>/`，不覆盖历史报告，也不清空演示订单。

当前 Compose 使用单节点 Redis，不会自动检测主从切换。脚本支持通过 `REDIS_CONTAINER` 指定容器，且会在预约处理完成后同时核对库存、资格和预约记录。报告中的预约延迟只代表接口受理时间，异步出票延迟需要另行测量。

调优过程、历史前后对比与踩坑记录见 [`PROGRESS.md`](../PROGRESS.md)。

## 七、Linux 入口验证

2026-09-08 在 WSL Ubuntu 中使用 Java 17、JMeter 5.6.3，对独立 `ticket-center-smoke` 环境验证：

- `smoke`：三个场景各 20 个请求，5 张票对应 5 笔订单，库存和预约记录核对通过。
- `full`：签到 10000 次、详情 4000 次、预约 1000 次，无异常响应；50 张票对应 50 个不同用户的订单，MySQL / Redis 剩余库存均为 0。
- 故意传入不存在的活动 ID：20 个详情请求全部被断言标记失败，入口退出码为 1，没有执行创建票档步骤。

这次验证确认 Linux 入口和结果校验能工作，不用于更新上面的历史性能数据。稳定吞吐和延迟仍需在相同环境与数据下重复测量，预约受理耗时不能代替异步出票耗时。

## 八、微服务拆分后复测（2026-09-11）

本节前半段被测服务为拆分后、优化前的 GHCR 镜像（commit `31b27421`），组合 `docker-compose.middleware.yml`、`docker-compose.init.yml`、`docker-compose.app.yml`，请求经 Gateway 进入；JMeter 仍在 Windows 主机，同机同计划同样本量，三轮连跑，第 1 轮为冷启动。

三个 `.jmx` 的断言统一为 JMeter 原生元素：签到、详情用 Response Assertion 子串匹配 `"code":200` 与 `"data":{...`；秒杀用 Regex Extractor 从 `"data":(\d+)` 取预约号，Response Assertion 以 OR 模式接受受理成功、已有有效预约、库存不足、限购一张四种结果。

### 实测结果

| 场景 | 第 1 轮（冷启动） | 第 2 轮 | 第 3 轮 | 单体基线稳态 |
| :--- | :---: | :---: | :---: | :---: |
| 签到状态 `GET /user/sign/status` | 1,710.9 / 108.5 ms | **3,749.5 / 42.5 ms** | **3,879.0 / 42.2 ms** | 2,860 ~ 3,005 / 60 ~ 65 ms |
| 演出详情 `GET /event/1` | 664.8 / 262.2 ms | **1,375.5 / 117.8 ms** | **1,527.9 / 105.5 ms** | 3,463 ~ 4,499 / 22 ~ 35 ms |
| 秒杀预约 `POST /ticket-orders/reserve` | 166.6 / 550.6 ms | **223.2 / 381.8 ms** | **243.1 / 356.6 ms** | 1,012 ~ 1,101 / 41 ~ 54 ms |

单位：吞吐量 req/s，斜杠后为平均耗时。三轮全部零错误，秒杀三轮对账均为 50 / 50 / 50，零超卖零少卖。


### 怎么读这三行

- **签到没有退化。** 拆分后签到走 Gateway → order-service，每请求仍是 3 次 Redis 往返（`hgetall`、`pexpire`、`get`，用 `INFO commandstats` 核过）。用停掉 Gateway 直连 order-service 的对照实验测得 Gateway 这一跳约占 7% ~ 12% 吞吐。
- **详情页慢 2.5 ~ 3 倍是真的。** 拆分后 `EventDetailVO` 命中聚合缓存之后还要经 OpenFeign 调订单服务查票档，订单服务那边直接查 MySQL（票档 join 库存加候补子查询），命中路径上多了一次 RPC 和一次数据库读。
- **秒杀慢 4.5 倍是真的。** 拆分后预约请求先落库再由恢复任务异步跑 Lua，被拒的请求也要进事务、排同一把票档行锁；100 并发 1,000 次请求里只有 50 次能成，其余 950 次全在锁上串行。

### 优化后复测（2026-09-12）

改动三处：详情页不再经 Feign 拉票档，票档列表由前端单独请求订单服务；秒杀受理先跑 Redis Lua 预扣，售罄和重复在 Redis 就拒掉，只有放行的请求进 MySQL 事务；票档状态与销售时间读 30 秒短缓存。同机同计划，三轮连跑。

| 场景 | 第 1 轮（冷启动） | 第 2 轮 | 第 3 轮 | 优化前稳态 | 单体基线稳态 |
| :--- | :---: | :---: | :---: | :---: | :---: |
| 签到状态 | 1,737.3 / 105.1 ms | **3,007.5 / 59.7 ms** | **3,635.0 / 49.4 ms** | 3,750 ~ 3,879 | 2,860 ~ 3,005 |
| 演出详情 | 1,896.6 / 86.9 ms | **2,511.0 / 59.6 ms** | **3,584.2 / 34.9 ms** | 1,376 ~ 1,528 | 3,463 ~ 4,499 |
| 秒杀预约 | 512.6 / 157.4 ms | **730.5 / 97.1 ms** | **727.8 / 101.2 ms** | 223 ~ 243 | 1,012 ~ 1,101 |

三轮零错误，秒杀对账全部 50 / 50 / 50。详情回到基线的 75% ~ 80%，秒杀回到 70%，剩下的差距是 Gateway 一跳和受理路径上仍保留的两次索引点查（活跃预约查重、幂等键）。票档短缓存单独测不出收益：加缓存前后两组稳态是 766 ~ 849 与 728 ~ 731，落在本机 30% 的同配置噪声里。

受理到出票的端到端延迟另测：受理事务提交后直接推送恢复任务，不再等每秒一次的扫描，三次实测受理后 225 ~ 278 ms 出现订单号。

### 客户端位置带来的延迟差

把 JMeter 放进容器、走 Docker 内网直连 order-service 时，签到平均耗时只有 8 ~ 10 ms；从 Windows 主机经 Docker Desktop 的端口转发打进去是 42 ~ 46 ms，每个请求多出约 35 ms。本报告所有耗时都含这一段，只能同方法之间比较，不能当作服务端处理时间。
